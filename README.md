# 有数收银：单店超市收银与远程监督系统

这是一个独立的单店收银应用，适合每班一名收银员、约 3000 个 SKU 的场景。系统使用 Node.js 内置 HTTP 服务和 SQLite，首次运行无需安装第三方包。

## 已实现

- 店主首次初始化、收银员独立账号、角色权限、账号停用和密码重设。
- 登录页提供“员工登录”和“店主登录”两个入口，共用相同账号密码表单。两种身份登录后进入收银台；员工菜单仅去掉“店主总览”和“员工账号”。员工可以只读查询商品库存及本人操作记录，店主可管理商品、账号并查看全店记录。所选身份须与账号角色一致。
- 商品维护、CSV 批量导入、扫码枪自动加购、支持的浏览器中使用摄像头扫商品条码、未知条码建档与店主审批、按件及按千克销售、售价历史、库存流水与抽盘差异。
- 店主可维护供应商、登记多商品到货单；确认到货会增加库存、记录每批商品的进货价，并更新最近进货成本。商品页可补录成本和查看按最近成本估算的库存价值。销售订单创建时会保存当时已知的成本快照，供后续毛利分析使用；员工接口不返回成本或供应商资料。
- 收银购物车、顾客屏、整单折扣与单品改价审批、现金实收与找零、浏览器打印订单。
- 班次备用金、现金补入／支出／入库、非销售开钱箱记录、盲点交班与现金差额。
- 微信／支付宝订单登记为待核实；店员可记录顾客付款详情中的交易号（仅是线索）；店主导入规范化渠道交易流水后，按订单号或交易号、渠道和金额匹配；固定码流水也可手动匹配。
- 全额退款申请、店主审批、现金退款与外部渠道退款凭证记录。
- 店主看板：待审批、待核实支付、渠道有款无单、现金差额、库存差异、每周约 10 种商品的抽盘清单和操作审计；最近 13 个自然月（含本月）的收款、退款、净额、订单数与支付渠道明细。看板经营数据每 10 秒自动刷新；抽盘清单在进入看板或手动刷新时更新。月报查询范围仅限最近 13 个月，原始订单和审计记录不会自动删除。
- 店主「月度盘点（可选）」用于深入核查：按商品比较期初实盘、入库、其他库存调整、期末实盘和系统出库，可逐项录入或批量导入 CSV，筛选差异并导出全量对账表。没有实盘数据的商品不会被误判为已对平。
- 本地 SQLite 数据库、事务处理、每日备份文件（运行期间每小时刷新一次当天备份）。

## 启动

需要 Node.js 24 或更高版本。进入此目录运行：

```bash
node server.js
```

这是本地开发版。若已配置 `POS_DB_PATH`，请用该路径启动，避免与其他门店数据混用。首次正式使用前先用真实商品 CSV 初始化商品，并用店主账号检查收款方式、金额和交班流程。

打开 <http://127.0.0.1:3100>。首次运行时，终端会显示一次性初始化口令；在页面创建店主账号。数据库保存在 `data/pos.sqlite`，备份保存在 `data/backups/`。店主创建收银员账号后，可在「商品与库存」导入商品，在「班次与现金」开班。

可选环境变量：

```text
POS_PORT=3100                     服务端口
POS_HOST=127.0.0.1                监听地址，默认仅本机
POS_DB_PATH=/path/to/pos.sqlite   数据库文件路径
POS_SETUP_TOKEN=...               固定首次初始化口令；不设置则启动时随机生成
POS_PUBLIC_ORIGIN=https://...     经 HTTPS 反向代理访问时的浏览器来源
```

顾客屏地址是 <http://127.0.0.1:3100/customer.html>，可在同一浏览器的第二窗口打开，放到面向顾客的显示器上。它通过浏览器内的 BroadcastChannel 显示当前购物车，仅适合同一浏览器／同一设备的双屏场景。

## 实际收银顺序

1. 店主录入商品、供应商并创建收银员账号；到货后在「采购与供货」扫描条码、填写数量和进货价，确认入库。
2. 收银员开班，录入备用金；把光标放在商品搜索框，扫码枪读到已录入的完整条码后会自动加购，扫码枪发送回车也可以。支持的浏览器还可点「打开摄像头扫码」。称重商品扫码后请填写实际重量。
3. 现金订单填写实收金额后完成销售。改价或折扣订单先由店主审批。
4. 扫码订单先进入「待核实付款」。若顾客能出示付款详情中的渠道交易号，店员可登记；这不会把订单标记为已到账。店主从实际商户渠道取得交易流水并导入后，系统按交易号、渠道和金额匹配。没有登记交易号的订单可由店主手动匹配。
5. 员工交班时先输入实点现金；提交后系统计算应有金额和差额。店主查看异常并记录结论。

## CSV 导入格式

商品文件使用 UTF-8 CSV。单位只能是 `piece`（件）或 `kg`（千克）；价格单位是元，最多两位小数；库存最多三位小数。`cost_yuan` 为可选的最近进货成本列，留空不覆盖已有成本。重复条码会更新名称和售价，保留已有库存。已有商品不能直接更改计量单位，避免库存单位被错误解释。

商品表不完整也可以先使用：店主在「商品与库存」扫描新条码，填写名称、售价与库存后保存；如果从收银台发现新条码，店主可点「立即建档并加购」。收银员扫到新条码时，可填写包装名称和货架建议价并提交申请；店主在「店主总览」核对后批准建档，员工重新扫描即可销售。未经批准的建议价不能用于收款。

如果原始资料是 Excel，请先在 Excel 中另存为 UTF-8 CSV，再按下方列名导入。导入后，在「商品与库存」的条码栏用扫码枪或摄像头扫描已有商品，会带出本店记录的名称、单位和售价。条码本身不包含店铺售价。

```csv
barcode,name,unit,price_yuan,cost_yuan,stock
6900000000011,矿泉水,piece,2.50,1.20,30
6900000000028,散装苹果,kg,8.90,5.40,15.500
```

支付流水文件是**从实际商户平台或支付服务商账单整理出的规范化 CSV**。仅接受状态 `SUCCESS` 的收款交易；`order_id` 填本系统完整订单号。固定收款码交易没有本系统订单号时，可留空；若员工已登记相同渠道交易号且金额一致，导入后自动匹配，否则由店主按交易号、金额和时间人工匹配。退款流水需单独核对，不要作为收款行导入。

```csv
channel,transaction_id,order_id,amount_yuan,status,paid_at
wechat,渠道交易号,本系统完整订单号,12.50,SUCCESS,2026-10-12T10:00:00+08:00
```

不同服务商的原始导出列名可能不同，导入前须转换为上述格式。系统会拒绝金额、渠道或订单状态不匹配的自动核销，并将无法匹配的流水列为异常。

## 采购与供货

「采购与供货」目前记录到货和库存，不管理供应商应付款、采购退货或电子发票。库存估值按最近进货成本估算，尚未录入成本的商品不计入；它不是财务存货计价。后续可基于到货明细、成本历史、库存流水和销售成本快照制作可视化看板。

## 低工作量监督流程

1. 收银员日常扫码收银、按实际到货入库，每班结束时先盲点现金。店主打开「店主总览」，优先处理现金差额、退款或改价审批、负库存等异常。
2. 店主定期从微信、支付宝实际商户渠道导出账单并批量导入。系统自动匹配可核实的扫码订单；店主只处理剩余的待核实订单或有款无单流水。固定收款码尚未接入真实到账接口，导入前系统无法确认到账。
3. 每周由店主或可信任的人现场抽盘看板推荐的约 10 种商品。清单每周固定，综合近期销量、历史盘点差异、盘点间隔及轮换抽检生成。输入实点数量后，系统记录完成进度，并将数量差异列为库存异常。已经登记的商品本周不用重复盘点。
4. 发现差异时才追查该商品的进货、销售、库存调整与操作记录；必要时再使用「月度盘点（可选）」扩大核查范围。日常不要求月初、月末盘完约 3000 种商品。

系统账面库存依赖商品初始库存、到货、销售及库存调整如实录入。少量抽盘能降低店主工作量，但不能保证发现所有漏扫商品、账外现金或虚报现金实点。现金和扫码收款仍需结合独立的现金交接或存款记录、真实渠道账单核对。

## 月度出货核对

需要深入核查时，店主进入「月度盘点（可选）」，选择最近 13 个月内的月份。对要核查的商品填写期初和期末实际盘点数量；若上月已录入期末数量，本月可自动沿用为期初。本月新建商品的期初默认为零，建档时登记的初始库存计入本月入库。可以逐项保存，也可下载包含全部商品的盘点 CSV 模板，填入 `opening`、`closing` 后批量导入；留空不会覆盖旧值。整月核查应依据当时的纸质或电子盘点记录，不能用今天的库存倒填过去月份。

计算口径：`实际出货 = 期初实盘 + 到货及新商品初始入库 + 其他库存调整净额 − 期末实盘`；`差异 = 实际出货 − 系统销售出库`。系统销售出库按库存流水中的现金销售、扫码待核实出库、取消回库和退款回库净额计算。正差异表示少货，负差异表示多货。普通抽盘产生的账面修正不计入其他库存调整，避免把盘亏自动抵消。期初或期末实盘缺失时不计算差异；本月未结束时结果仅供阶段性查看。录入月度实盘不自动改动当前库存，需要修正账面库存时请在「商品与库存」另行抽盘。差异只说明数量不符，不能单独证明原因或责任人。

## 真实支付与设备接入

当前版本**没有调用微信、支付宝或聚合支付服务商的真实收款接口**，也不会生成真实付款二维码。店员不能在系统里自行点击“扫码已到账”。扫码业务能否在收银台即时确认，取决于商户号／服务商是否提供下单、查单、支付通知、退款和账单接口。接入时应把商户凭证只放在服务端，并以渠道签名结果和主动查单为准。请提供你实际使用的服务商名称和接口文档，以便继续完成该适配。

扫码枪按键盘输入工作；摄像头识别优先使用浏览器原生 `BarcodeDetector`，不支持时回退到随系统提供的 ZXing 条码识别组件。摄像头仍需要安全页面（本机 localhost 或 HTTPS）及浏览器授权。订单小票通过浏览器打印。实体钱箱、电子秤和打印机驱动尚未接入；「登记非销售开钱箱」只留下操作记录，不会控制实体钱箱。顾客屏和库存抽盘可辅助发现漏扫，无法单独证明每件离店商品都已录入。

ZXing 浏览器组件来自 [zxing-js/browser](https://github.com/zxing-js/browser) 的 `0.2.1` 版本，MIT 许可证见 `licenses/zxing-browser-MIT.txt`；运行时从本机加载，不依赖外部 CDN。

开发方案中涉及的**实时渠道通知／查单、动态二维码、收银员扫顾客付款码、渠道退款接口、手机主动推送、现金面额输入、无条码临时商品**还没有接入。当前固定码对账由店主导入渠道账单触发，不会在顾客扫完码的瞬间自动确认。店主总览要主动打开或刷新；当前不会向手机发送推送消息。要让店主在店外访问，还需要部署到 HTTPS 服务或安全 VPN。

## 运行与数据安全

- 默认只监听本机 `127.0.0.1`。店主要从店外手机访问时，应部署到 HTTPS 环境或安全 VPN，并配置 `POS_PUBLIC_ORIGIN`；不要直接将无 TLS 的端口暴露到公网。
- 操作数据库文件和备份文件只应由店主或运维人员访问。当天备份位于同一磁盘，仍需定期复制到另一处安全存储，才可防止设备损坏导致数据全失。
- 每个员工使用独立账号；停用或重设密码会使其现有会话失效。口令、支付服务商私钥、正式数据不要提交到仓库。
- 上线前应导入真实商品资料、核对库存开账、跑至少 7 个营业日的并行对账，并与支付服务商联调失败、超时、退款和重复通知等情形。
